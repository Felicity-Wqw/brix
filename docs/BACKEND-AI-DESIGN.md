# 后端架构与 AI 服务设计（简版）

> 物归校园 · Spring Boot 3.5 单体分层 + LangChain4j 三智能体
> 配套细节见 [DESIGN.md](DESIGN.md)（架构图 / E-R 图）与 [API.md](API.md)

---

## 一、后端架构

### 分层结构

```
Controller（11 个，42 接口）→ Service（业务与事务边界）→ Mapper（MyBatis-Plus）→ MySQL（12 表）
                    ↑ Security（JWT 鉴权）        ↑ AI 模块（可选装配）↑ 定时任务 / WebSocket
```

统一响应体 `R{code,msg,data}`，业务失败 HTTP 仍 200 由 `code` 判断；`Long` 全部序列化为字符串防精度丢失；三张表以上写操作与资金流转统一由 `@Transactional` 包裹。

### 商品购买全流程（约 200 字）

买家在详情页点「我想要」，选面交（时间地点）或邮寄（收货三件套）创建订单，状态为待付款、商品仍在售。买家进收银台，微信/支付宝沙箱确认后调用支付：系统用条件更新把商品从在售抢占为已售（`WHERE status='ON_SALE'`，影响行数为 0 即已被抢），订单推进为待面交或待发货，并关闭同商品其它待付款单——同一事务完成，靠行锁原子性防超卖。付款即进入平台托管。卖家发货后买家确认收货（面交单直接完成），同事务写入 `settle_time`，托管释放、款项结算给卖家；买家取消或超时未付则定时关单、商品回滚在售。

## 二、AI 服务设计

### 搭建方式

AI 能力以 **LangChain4j + DeepSeek**（`deepseek-chat`）接入，通过 `ObjectProvider` **可选装配**：`AI_API_KEY` 存在则注入 LLM 实现，缺失或调用失败自动降级为本地规则引擎（`RuleBasedEstimator`）——估价、文案、审核三条链路都有降级实现，**系统永不因 AI 故障而不可用**。密钥与模型名走环境变量（`AI_API_KEY / AI_BASE_URL / AI_MODEL`），代码中不出现任何凭据。

### 三个智能体

| 智能体 | 职责 | 关键技术点 |
| --- | --- | --- |
| 估价 | 给出建议价、区间、置信度、依据 | **两阶段**：无原价时先查 LLM 新品价作锚点，再综合成交库定价；模型通过**工具调用**实时查库 |
| 文案 | 生成标题 + 三段式描述 + 标签 | 按分类定制卖点框架，内置合规红线（绝对化用语/医疗功效/站外引流） |
| 审核 | 发布合规第二道闸 | 四选一判定（通过/驳回下架/修改重审/上报风控），只拒不放行敏感内容但不能阻断发布 |

### 两阶段估价流程

```
入参(品牌型号/成色/原价?) 
  → ① 无原价？调 LLM 知识库估「全新参考价区间」，×成色折价系数得第二锚点
  → ② 主估价：注入【定价参考数据包】+ 模型自主调工具查成交库
       soldPriceStats（90 天成交笔数/中位数/区间/成交样本标题）
       onSaleLowestPrice（同款在售最低价）· conditionDiscountFactor（成色系数）
  → ③ 同款判定：成交样本标题与待估商品不是同一具体产品 → 忽略该数据
  → ④ 结果清洗：二手价硬钳制 ≤ 原价×0.98、区间合法化、依据不少于 2 条
  → 输出 JSON（suggestPrice / priceRange / confidence / reasons / riskTips / source）
```

### 工程化约束

- **额度**：每用户每日 10 次（审核调用不计入用户额度），用量记 `t_ai_estimate_log`
- **来源透明**：返回值 `source` 字段区分 `LLM` / `RULE`，前端如实展示
- **结果兜底**：JSON 解析失败、超时、额度超限、无 Key 全部走规则引擎，接口仍返回 200
- **幻觉控制**：不允许编造成交数字（必须来自工具）、不允许估价高于原价、引用 AI 知识库价格必须注明「仅供参考」

---

## 三、一句话总结

后端是「分层单体 + 事务化状态机」，把二手交易的每个状态变化都收敛在数据库事务里；AI 是「可选装配的增强层」，有则更聪明、无则仍可用，所有输出都经过清洗与钳制——**AI 只做增强，不做依赖**。
